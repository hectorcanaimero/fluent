# PR-01 · Modelo de datos (SPEC-01) — pendientes y decisiones sin spec

Registro de todo lo que SPEC-01, SPEC-05 o SPEC-07 no dicen y hubo que decidir
al implementar el modelo de datos, siguiendo la regla de
`docs/tasks/README.md`: no inventar, anotar y elegir lo más simple. Cada
entrada dice qué se decidió y qué habría que confirmar.

Un archivo por PR para que dos sesiones en paralelo no se pisen. El de PR-08
está en `docs/specs/PENDIENTES.md`.

### 1. `groups.owner_id` es nullable y se borra con `ON DELETE SET NULL`
SPEC-01 §2.2 declara `owner_id uuid FK auth.users(id)` sin decir qué pasa al
borrar la cuenta. El PRD exige "borrado de cuenta completo bajo pedido", así que
la columna queda nullable y el borrado del operador no bloquea. **A confirmar:**
qué hace SPEC-05 §4 (resumen semanal) si el grupo se queda sin owner con
credencial.

### 2. `group_members` es una vista SECURITY DEFINER, no SECURITY INVOKER
SPEC-01 §3 pide que la vista sea SECURITY INVOKER y a la vez que `profiles`
limite el SELECT a la fila propia. Ambas cosas juntas son imposibles: con
SECURITY INVOKER la vista hereda la RLS de `profiles` y un usuario no vería a
sus compañeros. Se deja la vista con el modo por defecto (definer, dueño
`project_admin`) y el filtrado por grupo lo hace su `WHERE` con
`public.current_group_id()`, que es el patrón de "public projection" de la guía
de control de acceso de InsForge. La tabla base sigue cerrada a la fila propia.
**A confirmar:** actualizar el paréntesis de SPEC-01 §3.

### 3. `redeem_invitation` acepta un segundo parámetro opcional
SPEC-01 §5 la declara como `redeem_invitation(code)` y dice que la llama la API,
que usa la clave admin; con esa clave `auth.uid()` es nulo y la función no sabría
a quién asignar el grupo. Firma final:
`redeem_invitation(p_code text, p_user_id uuid DEFAULT NULL)`, que usa
`auth.uid()` cuando no se pasa el segundo argumento. Compatible con la llamada
de un token de usuario.

### 4. `profiles.suggested_level`
No está en SPEC-01 §2.1 pero sí en SPEC-05 §2 y en el alcance de PR-01/T1. Se
añade como `text CHECK (suggested_level IN ('A2','B1','B2'))`, nullable.

### 5. Alfabeto y coherencia de `invitations`
SPEC-01 §2.3 dice "8 caracteres, alfabeto sin ambigüedad (sin 0/O/1/I)" sin
fijarlo. Se concreta como `^[A-HJ-NP-Z2-9]{8}$` (mayúsculas y dígitos 2-9). Se
añade un CHECK de coherencia `(used_by IS NULL) = (used_at IS NULL)`.

### 6. Verificación de email desactivada en la rama de InsForge
Para poder probar la RLS con tokens de usuario reales se aplicó
`require_email_verification = false` **solo en la rama `feat-datos`**. El
proyecto principal sigue con la verificación activa: desactivarla es trabajo de
PR-08/T2 (SPEC-06 §6). El `insforge.toml` no se versiona en este PR porque la
configuración del proyecto es alcance de PR-08.

### 7. Los tests SQL no pueden cambiar de rol
`db query` de InsForge rechaza cualquier cambio de configuración de sesión
("Changing SQL session configuration is not allowed"), así que un test SQL no
puede hacer `SET ROLE authenticated` para ejercitar la RLS. Reparto:
- Las políticas RLS se comprueban por REST con tokens reales en
  `apps/api/scripts/db-smoke.ts`.
- La lógica de las funciones (`redeem_invitation`, `close_session`, …) se
  comprueba en `apps/api/migrations/tests/*.sql`.

### 8. Usuarios de prueba fijos para los tests SQL
`auth.users` es una tabla gestionada por InsForge y solo se escribe desde la API
de auth, así que los tests SQL no pueden crear usuarios. `apps/api/scripts/db-test-users.ts`
crea de forma idempotente `sqltest-{a,b,c,d}@fluent.test` y los tests los buscan
por email. Son datos de la rama de InsForge; `branch merge` solo lleva esquema.

### 9. CHECK de proveedor también en `model_preferences.chat_provider`/`brief_provider`
SPEC-01 §2.5 no declara un CHECK para `chat_provider` ni `brief_provider` (solo
dice `DEFAULT 'openrouter'`), a diferencia de `provider_credentials` (§2.4), que
sí limita `provider IN ('openrouter','gemini')`. Para que la columna nunca
contenga un proveedor que la API no sepa resolver, se añade el mismo CHECK
`IN ('openrouter','gemini')` a ambas columnas de `model_preferences`. El
catálogo de *modelos* concretos por proveedor lo sigue validando la API, tal y
como dice la spec; el CHECK solo cierra el conjunto de proveedores.
**A confirmar:** si en el futuro se admite un tercer proveedor, hace falta una
migración que amplíe el CHECK en las dos tablas a la vez.

### 10. `model_preferences`: sin INSERT ni DELETE desde `authenticated`
SPEC-01 §3 dice "UPDATE propia" para `model_preferences` sin mencionar INSERT ni
DELETE, y el propio PR-01/T2 aclara que "los crea la API con la clave admin". Se
interpreta como: la app (rol `authenticated`) solo tiene `GRANT SELECT` y
`GRANT UPDATE` (sobre las cuatro columnas mutables) — nunca `INSERT` ni
`DELETE`. La fila se crea al terminar el onboarding y solo la borra la API si
hiciera falta (p. ej. al desconectar todos los proveedores del usuario).

### 11. `provider_credentials`: ni GRANT ni política para `authenticated`
SPEC-01 §2.4 dice "ninguna política para `authenticated`", pero no dice si además
hay que revocar los GRANTs por defecto de InsForge. Se hace lo mismo que en el
resto de tablas sensibles de esta migración: `ALTER TABLE ... ENABLE ROW LEVEL
SECURITY` más `REVOKE ALL ... FROM anon, authenticated`, y ningún `CREATE
POLICY` ni `GRANT` para esos roles. Así la tabla queda cerrada por dos capas
(sin privilegio SQL y, aunque lo tuviera, sin política RLS que le abra ninguna
fila), en vez de depender solo de la ausencia de políticas.

### 12. `xp_events.kind` incluye `streak_7`
SPEC-01 §2.13 lista `'session','duration_bonus','double_day','boss','challenge'`,
pero SPEC-07 §2 emite además un evento `streak_7` con `XP_STREAK_7_BONUS`. El
CHECK admite los seis valores. El multiplicador de boss se aplica sobre la base y
la duración, así que queda registrado dentro de los eventos `session` y
`duration_bonus`; `boss` sigue en el catálogo sin emisor. **A confirmar:** si se
prefiere una fila `boss` aparte con la diferencia, hay que cambiar SPEC-07 §2.

### 13. `sessions.challenge_from_user_id` se adelanta a PR-01
SPEC-01 §2.6 no la lista, pero SPEC-07 §2 la necesita para el bonus de desafío
dentro de `close_session`. PR-07/T1 preveía añadirla en su propia migración; se
adelanta aquí para que `close_session` implemente SPEC-07 §2 sin ramas muertas.
PR-07 ya no necesita esa migración pequeña.

### 14. FKs diferidas en `sessions`
`sessions.news_item_id` y `sessions.callback_fact_id` apuntan a `news_items` y
`facts`, que nacen en las migraciones 5 y 4. En la migración 3 se declaran como
`uuid` sin FK y cada migración posterior añade su `ALTER TABLE ... ADD FOREIGN
KEY`. El orden de migraciones de SPEC-01 §6 no permite otra cosa.

### 15. `close_session` es idempotente
SPEC-04 §5 y §6 dejan que la cierren tanto la API como el job `session-sweeper`.
Si la sesión ya no está `active`, la función no vuelve a puntuar: devuelve el
`xp_earned` que ya tenía y el streak actual. Sin esto, dos cierres duplicarían XP
y `xp_events`.

### 16. El bonus de los 7 días solo se paga cuando el streak avanza
SPEC-07 §2 dice `si streak % 7 == 0 → xp += XP_STREAK_7_BONUS` justo después del
bloque de streak, que en la rama "last_session_day = hoy" no hace nada. Aplicado
al pie de la letra, la segunda sesión del día volvería a cobrar el bonus con un
streak múltiplo de 7. Se paga solo cuando el streak cambia en esa llamada.
**A confirmar:** matizar SPEC-07 §2.

### 17. El "día" de las sesiones válidas se cuenta por `ended_at`
SPEC-07 §2 dice "sesiones ended del usuario con `xp_earned > 0` en su hoy local"
sin decir si el día lo marca `started_at` o `ended_at`. Se usa `ended_at`, que es
cuando se concedió el XP, convertido a la zona horaria del perfil.

### 18. `migrations/tests/` rompe el CLI de InsForge
`insforge db migrations new|up` valida el nombre de todas las entradas de
`migrations/` y aborta con `Invalid migration filename: tests` al ver el
directorio de tests que piden SPEC-01 §6 y PR-01. Se añade el envoltorio
`apps/api/scripts/db-migrate.sh`, que aparta `migrations/tests/` mientras corre
el comando y lo devuelve al terminar. Reportado a InsForge con
`npx -y @insforge/cli feedback`.

### 19. Las funciones RPC devuelven `jsonb`
SPEC-01 §5 dice que `pick_callback_fact` "devuelve la fila o null" sin fijar el
tipo. Todas las funciones RPC de este PR devuelven `jsonb` (`NULL` cuando no hay
resultado), porque es lo que PostgREST expone de forma uniforme por
`/api/database/rpc/<fn>` y evita depender del `ROWTYPE` de una tabla que puede
cambiar. La API mapea a su DTO.

### 20. Criterio exacto de `pick_callback_fact`
SPEC-01 §5 pide "un hecho `confirmed` no usado en la última sesión, priorizando
los que tienen `happens_on` reciente". Concretado así:
1. Se descarta el hecho con `last_used_at` más alto, salvo que sea el único
   candidato (así nunca sale el mismo dos veces seguidas sin depender de la
   tabla `sessions`).
2. Orden: primero los que tienen `happens_on`, por distancia a `current_date`;
   luego los que nunca se usaron (`last_used_at NULLS FIRST`), menor
   `use_count` y más antiguos.
`last_used_at` se marca con `clock_timestamp()` y no con `now()`: dos llamadas
dentro de la misma transacción comparten `now()` y "el último usado" dejaría de
estar definido. `current_date` es la fecha del servidor (UTC), no la del perfil;
para elegir un hecho la diferencia de unas horas es irrelevante.

### 21. Firma y garantías de `apply_brief`
SPEC-05 §2 la nombra como
`apply_brief(session_id, brief, level_hint, recurring_errors, facts[])`. La
firma real es
`apply_brief(p_session_id uuid, p_brief text, p_level_hint text DEFAULT NULL,
p_recurring_errors jsonb DEFAULT '[]', p_facts jsonb DEFAULT '[]')`, con los
hechos como array jsonb de `{ text, happens_on }`. Añadidos que la spec no
detalla y que el job necesita:
- Es idempotente: si la sesión ya está `brief_job_status = 'done'` devuelve
  `{ applied: false }` sin tocar nada (SPEC-05 §1 exige jobs idempotentes).
- Recorta el brief a 600 caracteres, los hechos a 160 y los errores
  recurrentes a los 5 primeros, en vez de fallar por CHECK.
- Un brief vacío lanza `BRIEF_EMPTY`.
- La deduplicación usa `public.normalize_fact_text()` (minúsculas, todo lo que
  no sea alfanumérico pasa a espacio, sin espacios sobrantes), compartida por
  la función y por el índice `facts_user_normalized_idx`.
- La regla de `suggested_level` (tres briefs seguidos con otro nivel) vive en
  el job de PR-05, no en SQL.

### 22. `coaching_brief_history` no la expone la app
SPEC-01 §2.10 la crea como material de estudio y §3 no le da fila en la tabla de
políticas. Se queda cerrada como `xp_events` o `llm_calls`: RLS activada, sin
GRANT ni política para `authenticated`. **A confirmar:** si la app llega a
mostrar la evolución del brief, hará falta una política de lectura propia.

### 23. `weekly_leaderboard`: guarda contra grupo cruzado
SPEC-01 §5 dice que la llaman "app y API" pero no dice cómo se le impide a un
usuario pedir el leaderboard de un grupo ajeno pasando cualquier `group_id`: al
ser `SECURITY DEFINER` y tener `GRANT EXECUTE` para `authenticated`, sin este
chequeo cualquier usuario autenticado podría leer el XP y las sesiones de
cualquier otro grupo. Se añade: si `auth.uid()` no es nulo (llamada con token
de usuario) y `public.current_group_id()` es distinto del `p_group_id`
pedido, `RAISE EXCEPTION 'FORBIDDEN'`. Con la clave admin `auth.uid()` es nulo
y no se aplica el filtro, porque la API (SPEC-05 §4, jobs) necesita poder
consultar cualquier grupo. Probado por REST en `db-smoke.ts` (T5).

### 24. `apply_streak_grace`: tercera rama para idempotencia
SPEC-05 §6 paso 1 describe solo dos casos ("si no practicó ayer: si es
elegible para gracia, se la da; si no, streak a 0"), aplicado a `last_session_day
< ayer`. Al pie de la letra, un perfil al que ya se le concedió la gracia hoy
(`last_session_day = anteayer`, `grace_used_week = lunes_actual`) volvería a
caer en el `else` de "no es elegible" en una segunda ejecución del job el
mismo día, y se le pondría el streak a 0 justo después de haberle concedido la
gracia. SPEC-05 §1 exige que todos los jobs sean idempotentes, así que se
añade una tercera rama explícita: si la gracia de esta semana ya se aplicó
(mismos dos campos), no se toca nada. **A confirmar:** matizar SPEC-05 §6 con
este tercer caso.

### 25. `update_group_streaks`: RPC y columna `group_streak_day` nuevas
Ni SPEC-01 §5 ni SPEC-05 §6 nombran una función para el paso 2 de
`daily-streaks` (streak grupal): la spec solo da la regla de negocio. Se crea
`public.update_group_streaks()`, `SECURITY DEFINER`, sin `GRANT` para
`anon`/`authenticated` (la llama solo el worker con la clave admin, igual que
`apply_streak_grace`). Para que sea idempotente si el job se reintenta o se
ejecuta dos veces el mismo día, se añade `groups.group_streak_day date`: el
último día (UTC, `current_date`) en que se actualizó ese grupo; si ya coincide
con hoy, la función se salta el grupo. Sigue el mismo patrón que
`profiles.last_session_day` en `close_session`. **A confirmar:** documentar la
función y la columna en SPEC-01 §2.2 y §5, y en SPEC-05 §6.
