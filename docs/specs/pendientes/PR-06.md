## PEND-01 · SPEC-02 §4.1 · `providers[].status` de `GET /me`: la app comparaba contra `'connected'`, la API real devuelve `'active'`

`apps/api/src/credentials/credentials.repository.ts` (`ProviderConnectionStatus`) usa los cuatro
valores `'active' | 'revoked' | 'error' | 'not_connected'` (`CredentialStatus` de SPEC-01 §2.4 más
el sintético `'not_connected'` de PEND-15/PR-02). La app comparaba en ocho sitios contra el literal
`'connected'`, que la API real nunca envía — con `USE_FAKE_API=false` el banner "Conectá un
proveedor para practicar" habría bloqueado la práctica siempre, aunque el usuario tuviera un
proveedor activo, y la pantalla de proveedores nunca habría mostrado "Conectado" ni créditos.

**Corrección:** todos los `== 'connected'` pasan a `== 'active'`:
`lib/features/home/domain/home_data.dart::hasActiveProvider`,
`lib/features/providers/domain/providers_data.dart::isConnected`,
`lib/features/providers/presentation/providers_screen.dart` (carga de status, `isConnected` local,
switch de texto de estado), `lib/features/onboarding/presentation/onboarding_flow.dart` (salto a
`/providers` tras el onboarding), y los nueve usos de `'connected'` en `lib/core/api/fake_api.dart`
(para que la simulación deje de divergir del contrato real). `'revoked'` cae al mismo texto que
`'not_connected'` (rama `_` del switch): la UI no distingue "nunca conectado" de "revocado", que es
lo que ya hacía antes de este fix para cualquier valor que no fuera `'connected'`/`'error'`.

## PEND-02 · SPEC-02 §4.1 · `GET /me` no exponía `pendingActions`

`apps/api/src/profiles/profiles.types.ts::MeDto.pendingActions` (`string[]`, ver
`docs/specs/pendientes/PR-02.md` PEND-76) no existía en `MeResponse` (`models.dart`). Se agrega
`@Default(<String>[]) List<String> pendingActions` (freezed/json_serializable regenerados). Como
solo `WEEKLY_SUMMARY_NEEDS_CREDENTIAL` existe hoy y la API la calcula ya filtrada al owner del
grupo (PEND-76 de PR-02: la clave de Redis es `<ownerId>` = el `userId` de quien pide `/me`), la
app no necesita comprobar el rol: si la lista no está vacía, la acción es para quien la pide.
`HomeData.hasWeeklySummaryCredentialPending` expone ese único caso conocido; cualquier otro
identificador futuro se ignora sin romper nada (mismo criterio que ya documentó la API).

**Banner en Home:** `_PendingActionBanner` (`home_screen.dart`), visible cuando
`hasWeeklySummaryCredentialPending` es verdadero, con botón que navega a `/providers`. No hay
pantalla ni copy de referencia en SPEC-06 para este caso (la spec es de antes de PR-05); se optó
por el patrón ya usado para `_NoProviderBanner` (mismo estilo `goldSoft`) en vez de inventar un
componente nuevo.

## PEND-03 · SPEC-02 §6 · `ApiErrorCode` (Dart) no cubría `NOT_FOUND` ni `INTERNAL`

`apps/api/src/common/api-error.ts::API_ERROR_STATUS` tiene 16 códigos (los 14 de la tabla de
SPEC-02 §6 más las dos extensiones documentadas ahí mismo, `NOT_FOUND` 404 e `INTERNAL` 500,
añadidas por PR-02/T3). `ApiErrorCode` (`lib/core/errors/api_exception.dart`) solo tenía 14 más el
valor sintético `unknown`; un 404 de ruta inexistente o un 500 no controlado caían en `unknown`
igual que un error de red o un código realmente desconocido, indistinguibles para quien capture la
excepción. Se agregan `notFound` e `internal` a `ApiErrorCode` y a `fromWire`.

## PEND-04 · SPEC-02 §6 · `SESSION_ALREADY_ACTIVE`: `activeSessionId` va en el cuerpo, no dentro de `details`

`ApiException` (`apps/api/src/common/api-error.ts`) agrega `activeSessionId` como campo **extra**
junto a `error`/`message`/`statusCode` (`extra` se mezcla en el cuerpo top-level, nunca dentro de
`details[]`, que es solo para `VALIDATION`). El `ApiException` de Dart no tenía forma de leer ese
campo: `ApiClient.mapDioException` solo parseaba `data['details']`. Se agrega
`ApiException.activeSessionId` (`String?`) y `mapDioException` lo lee de `data['activeSessionId']`.
`FakeApi.createSession` metía el `activeSessionId` dentro de `details` (`[{'activeSessionId': ...}]`)
para simular el error: se corrige para usar el campo nuevo, consistente con la forma real. Ningún
test dependía de la forma vieja (no hay assertions sobre `details` de `SESSION_ALREADY_ACTIVE`).
Sesiones (`/sessions*`) no está fusionado (PR-04): esta corrección se valida contra el contrato de
`api-error.ts` (ya en `main`) y SPEC-02 §6, no contra un controlador de sesiones real.

## PEND-05 · SPEC-02 §4.5 · `getWeeklySummary` nunca detectaba `NOT_READY`

`HttpFluentApi.getWeeklySummary` distinguía "no hay resumen todavía" (`404 NOT_READY`) de un error
real con `e.toString().contains('NOT_READY')`. Como `ApiException.toString()` imprime el nombre
Dart del enum (`ApiErrorCode.notReady`), nunca la cadena `NOT_READY` de la API, esa condición jamás
era verdadera: cualquier `404 NOT_READY` real habría vuelto a subir como excepción no capturada en
vez de convertirse en `null` (que es lo que espera `GroupScreen._load`, aunque ahí el `catch (_)` lo
disimulaba igual). Se reescribe para capturar el `ApiException` que ya arma `ApiClient.guard` y
comparar `e.code == ApiErrorCode.notReady`.

## PEND-06 · SPEC-02 §4.1, `apps/api/src/content/interests.json` · el catálogo de intereses local no coincidía con el real

`GET /me` devuelve `interestsCatalog` con los 24 ids de `apps/api/src/content/interests.json`
(`technology`, `videogames`, `movies-series`, …), fijados por PR-02/T2. `kFallbackInterests`
(`lib/features/onboarding/data/interests_catalog.dart`) y el switch de
`lib/features/onboarding/domain/interest_labels.dart` tenían 24 ids **distintos**, inventados antes
de que existiera el catálogo real (`tech`, `gaming`, `daily_life`, `news`, `pets`, `politics`… — la
mayoría sin equivalente exacto en el catálogo real). Como `OnboardingFlow._loadCatalog` ya prefiere
`me.interestsCatalog` sobre el fallback (`me.interestsCatalog.isNotEmpty ? ... : kFallbackInterests`,
sin tocar), contra la API real esto no rompía el flujo, pero sí la traducción: cualquier id real sin
entrada en el switch cae a `_ => id` (el id crudo en inglés/kebab-case, por ejemplo "movies-series"
sin traducir) en vez de una etiqueta localizada — justo lo que dice de evitar SPEC-06 §4.5 en
general para textos de la UI.

**Corrección:** `kFallbackInterests` pasa a ser una copia exacta (mismos 24 ids, mismo orden) de
`INTERESTS_CATALOG_IDS` (`apps/api/src/content/interests.json`); `interest_labels.dart` traduce los
24 ids reales; se agregan las 24 claves nuevas (`interestTechnology`, `interestVideogames`,
`interestMoviesSeries`, …) a `app_es.arb` y `app_pt.arb` **en este mismo commit**, con las
traducciones `label_es`/`label_pt` que ya trae `interests.json` (la API las tenía preparadas para
esto). `FakeApi` reutiliza `kFallbackInterests` en vez de duplicar la lista, y su perfil de ejemplo
usa ids reales (`'travel', 'technology', 'movies-series', 'music'`). Se actualizó
`test/features/onboarding/onboarding_flow_test.dart` (claves `onboarding_interest_tech` →
`onboarding_interest_technology`, `onboarding_interest_movies` →
`onboarding_interest_movies-series`).

## PEND-07 · SPEC-02 §4.3 · endpoints de `/sessions*` validados contra la spec, no contra código real

PR-04 (sesiones) no está fusionado en `main` todavía (`apps/api/src` no tiene módulo `sessions`).
Las rutas, cuerpos y respuestas de `HttpFluentApi` para `/sessions/suggestions`, `POST /sessions`,
`POST /sessions/:id/turns`, `POST /sessions/:id/end`, `GET /sessions`, `GET /sessions/:id` se
revisaron contra SPEC-02 §4.3 y SPEC-04 (no contra un controlador real) y coinciden campo por
campo con lo que describen esas dos specs. Cuando PR-04 se fusione, hay que repetir esta
comparación contra el código real (`apps/api/src/sessions/`, si se llama así) antes de dar por
buena esta entrada.
